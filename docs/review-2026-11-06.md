## 核心问题（按优先级排序）

以下为仍存在的项目；本轮已修复项单列在后文。

### 1. 🟡 Major，网络失败仍可能被当成“没有记录”

定位：`composeApp/src/commonMain/kotlin/do_/linux/lindo/core/network/LinDoNetworkStack.kt:1359`、`:1448`、`:1678`、`:2225`。

通知、收藏、私信、草稿等接口仍在请求失败、非 JSON 响应或解析异常时返回空列表。即使空页面已经换成零度娘，用户仍可能看到错误的“没有内容”，无法区分断网、登录过期、站点验证和真正的空结果。部分大范围 `catch (Throwable)` 也吞掉协程取消，导致关闭页面后继续兜底请求。

方案：统一 `LoadResult<T>` / `LoadState`，保留 HTTP 状态、错误类型和缓存来源；仅成功的空数组显示 Empty。401 要求重新认证；403 区分站点验证；429 尊重 Retry-After；取消异常直接上抛。为每类列表补正常、空、断网、过期与限流测试。本轮先修复首页和详情的失败展示，其他接口需继续迁移。

### 2. 🟡 Major，原生帖子正文存在内容与交互损失

定位：`composeApp/src/commonMain/kotlin/do_/linux/lindo/core/render/DiscourseAstRenderer.kt:62`。

当前通过正则识别少量块级 HTML，再清除内联标签。链接语义、加粗/强调、表格结构、部分块外图片和 emoji 图片会丢失；投票、视频、数学公式等没有对应完整节点与交互。用户可能看不全原帖，而不是单纯排版不同。接口层有投票等方法不能证明正文已经具备对应功能。

方案：建立块级与内联 AST，保留链接、图片 alt、附件、表格、emoji 和嵌套结构；用脱敏的真实 cooked 样本回归。未支持的内容明确提供“查看原网页”全屏入口，避免静默丢弃。AST 缓存哈希碰撞与主线程解析已在本轮修复，内容完整性仍未完成。

### 3. 🟡 Major，构建工具链兼容性检查被绕过，Lint 结果不充分

定位：`composeApp/build.gradle.kts:74`、`:108`，`gradle/libs.versions.toml`。

当前 compileSdk 37、Kotlin 2.4 系列依赖与 AGP 8.13.2 组合超出该 AGP 文档所述支持范围；仓库同时关闭所有 AarMetadata 检查。Debug 能构建，但 D8 存在 Kotlin metadata 警告。Lint 命令虽成功完成，日志出现 Kotlin metadata 2.4/2.2 不兼容诊断，不能当作完整 Kotlin 静态分析通过。[AGP 8.13 官方兼容性说明](https://developer.android.com/build/releases/agp-8-13-0-release-notes)

方案：选定一套受支持的 AGP/Kotlin/Compose/Android SDK 组合，必要时采用新的 KMP Android 插件或回退相关依赖；恢复 AAR metadata 检查，重新跑完整 Lint、release 构建及安装验证。不要继续增加 suppression。当前 release 还未启用压缩，后续需独立验证 R8/资源裁剪与映射文件。本轮移除了另一台机器的硬编码 JDK 路径，并为 minSdk 24 启用 java.time 所需的 core library desugaring。

### 4. 🟡 Major，阅读上报队列在进程被终止时可能丢失

定位：`composeApp/src/commonMain/kotlin/do_/linux/lindo/core/connect/ConnectAndActivityEngine.kt:131`、`:241`。

队列仍保存在内存中。退到后台期间被系统杀进程、强制停止或设备重启，可能丢失未发送批次。修复正常退出页面的协程取消与重试，不等于实现持久化可靠投递。

方案：以账号、topic、post 与批次标识建立持久化队列，前台及时合并发送；确认服务端成功后再删除。处理重试去重、账号切换和存储上限，避免重复累计。补进程死亡、弱网与恢复场景。已移除“绝不丢数据”的不实注释。

### 5. 🟡 Major，认证存储与备份范围需要收紧

定位：`composeApp/src/androidMain/AndroidManifest.xml:8`、`composeApp/src/androidMain/kotlin/do_/linux/lindo/MainActivity.kt` 的会话持久化，以及 `CookieSentinel.ingestRawCookieString`。

`allowBackup=true`，会话偏好中存有 Cookie/API Key/待授权私钥，未配置明确的备份排除规则。共享 Cookie 模型从原始请求头恢复时也无法还原完整 domain/path/hostOnly 属性，不能宣称完整 RFC cookie jar。

方案：为云备份与设备迁移显式排除认证偏好、调试导入文件与 WebView 会话存储；将长期密钥纳入 Android Keystore 保护方案。浏览器会话以 CookieManager 为准，原生网络使用有域/path/过期信息的 cookie jar。本轮已经移除打开 WebView 时把主站 cookie 重建成 `Domain=.linux.do` 的逻辑，避免进一步扩大 host-only 范围。

### 6. 🟡 Major，120 Hz、复杂长帖与长期内存表现尚未完成真机验收

已请求 Android 支持的高刷新率类别，动画按系统时钟运行，没有把主线程锁在 60 fps；但测试设备是 60 Hz 模拟器。**请求高刷新率不等于设备持续输出 120 帧。** [Android 自适应刷新率说明](https://developer.android.com/develop/ui/views/animations/adaptive-refresh-rate)

方案：在支持 120 Hz 的中端和高端真机使用 release/profileable 包，针对含 GIF、长代码、图片、快速进出详情、旋转和恢复的场景采集 Macrobenchmark/Perfetto。分别报告 8.33 ms 帧预算、P95/P99、慢帧/冻结帧、GC、解码和主线程负载。`UserTitleTag` 的渐变及部分骨架屏仍逐帧在组合阶段读取动画值，需要通过重组计数确认成本，并优先移到绘制阶段。堆转储/LeakCanary 与 30 分钟以上重复导航后再判断泄漏；当前重复打开 WebView 的短测只能排除明显持续累积。

### 7. 🟢 Minor，交互尺寸、排版和细节仍需统一

首页和个人页仍有尺寸约 32 dp 的图标容器，多个次要标签使用 11 sp。文字本身的 bounds 不代表最终点击区域，不能简单据此认定全部不合格，但需要逐个核查实际 hit target 与语义。品牌矢量仍有较长路径，Lint 有 VectorPath 性能提醒。

方案：建立 4/8 dp 间距体系，主要正文约 14–16 sp、辅助文字优先 12–14 sp，图标可小但触摸区域至少 48 dp；验证系统 1.6/2.0 字体、深色对比度、TalkBack 顺序及横屏。细分高频小尺寸图标与大幅插画，继续简化路径，保留主体辨识度。已修复阅读页重复应用字号缩放，统一通用圆形按钮触摸区域；登录按钮 54 dp 已通过自动化检查。
